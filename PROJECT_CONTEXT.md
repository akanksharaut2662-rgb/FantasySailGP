## 3. The Decision — What We're Building

**Project Name (working title):** SailGP Game Engine
*(Not "Fantasy SailGP" — avoids trademark issues and the demo is historical scoring, not future prediction)*

### The Core Product

A data-driven fantasy scoring platform for SailGP fans, powered by real race telemetry.

**The full product loop:**
1. User opens the game and goes to build their fantasy team
2. **The optimizer** reads wind conditions and recommends which boats to pick → *"Model suggests AUS and GBR for today's conditions"*
3. User locks their team and runs a real historical race through the **scoring engine**
4. Points compute automatically from telemetry — speed, overtakes, finishing position, clean sailing
5. **Leaderboard** shows results AND shows how the model's recommendation actually performed

**The key framing:** The optimizer is not a bolt-on data science layer — it IS the recommendation brain that every real fantasy platform has. The fantasy game is the product; the optimizer is the intelligence inside it. One product, one narrative.

## 4. The Two Ideas We Evaluated (and Why We Chose This One)

### Idea A: Podium Predictor (rejected)
ML model predicting final race finishing positions from telemetry at any point in the race.

**Why rejected:**
- `TRK_RACE_RANK_unk` already exists — "current rank predicts final rank" is a trivial baseline the model struggles to beat
- Only 14 races total — too few to demonstrate robust ML
- The core finding ("races are decided mid-race") is not surprising
- Loses on storytelling, business value, and originality vs. Fantasy SailGP

### Idea B: SailGP Game Engine (chosen)
**Why chosen:**
- Wins on 4 of 6 judging criteria: originality, business value, design, presentation
- "Fantasy football for sailing" — most quotable pitch in the room
- Working demo is natural: pick → race runs → points → leaderboard
- Clear business model (sponsorable categories, broadcaster integration)

## 5. Technical Architecture

### Component 1: Scoring Engine

Reads a real race CSV and computes fantasy points per boat.

| Category | Source column | Notes |
|---|---|---|
| Speed points | `BOAT_SPEED_km_h_1` | Mean or top speed, normalized by wind (TWS) ideally |
| Finishing position | `TRK_RACE_RANK_unk` at last row where status=3 | |
| Overtakes | Changes in `TRK_RACE_RANK_unk` during race | `rank[t] < rank[t-1]` = overtake |
| Clean sailing | `TRK_PENALTY_COUNT_unk` at race end | Fewer penalties = more points |
| VMG consistency | `VMG_km_h_1` std dev | Lower variance = bonus points |

**DNF/OCS handling:** boats with `TRK_BOAT_RACE_STATUS_unk` ≠ 3 at race end get zero finishing points. Define this rule explicitly before building.

### Component 2: Pre-Race ML Optimizer

Predicts expected fantasy points per team given wind conditions. This is the technical/data science layer.

**Training data structure:**
```
team=AUS, avg_tws=28.3, avg_twd=215 → fantasy_points=340
team=GBR, avg_tws=28.3, avg_twd=215 → fantasy_points=290
team=CAN, avg_tws=28.3, avg_twd=215 → fantasy_points=210
... (60 rows from Halifax)
```

**Critical note:** Wind is race-level (same for all boats in a race). So `team` identity MUST be a feature — it encodes which teams perform well in which conditions. Without team as a feature, every boat in the same race has identical inputs.

**Model recommendation:** Logistic regression or XGBoost (simple — 60 training rows is too few for complexity).

**Train/test split (confirmed decision):**
- Train on Halifax (60 rows: 6 races × 10 teams)
- Validate on Bermuda (96 rows: 8 races × 12 teams)
- Narrative: *"We trained on Halifax 2024, then asked what the model would have recommended for Bermuda 2026."*

**Framing with judges:** Honest proof-of-concept. When Hornsby asks "how many data points?" — answer is 60, and say exactly that. Explain it scales with more race data.

**Validation approach:** Leave-one-race-out cross-validation on Halifax, then full test on Bermuda.

### Component 3: UI / Demo

**Team builder screen:** user picks fantasy lineup. Optimizer recommendation shown alongside.
**Race scoring view:** real race replays, points tick up per category with callouts.
**Leaderboard:** final standings with breakdown.
**Animated race replay (stretch goal):** boats moving on GPS map while points accumulate.

**Tech stack decision (still needed):**
- **Streamlit (Python):** faster to ship, easier data pipeline, less polished
- **HTML/JS web app:** more polished, harder to wire data layer

## 6. Tim Hornsby Risk — Defense Prep

He will ask domain-specific questions. Prepared answers needed for:

**Q: "Why do you score overtakes? Gate selection matters more in SailGP."**
A: We score rank improvements as a proxy for aggressive racing and comeback ability. We acknowledge gate selection is tactically important — a future version would score gate choice explicitly using mark data.

**Q: "How did you define best maneuver?"**
A: Speed recovery after a tack/gybe — the boat's speed relative to its pre-maneuver speed within a 10-second window. We detect tacks/gybes from heading changes (`RATE_YAW_deg_s_1` + `TWA_SGP_deg` sign flip).

**Q: "Your speed scoring — is it wind-normalized?"**
A: Yes — we normalize `BOAT_SPEED_km_h_1` by the race's `avg_tws_km_h` from metadata. Same speed in 30 knots vs 15 knots is scored differently.

    racing = df[df["TRK_BOAT_RACE_STATUS_unk"] == 2]
